# Chioma Infrastructure (Terraform)

All AWS infrastructure for Chioma is defined here so any environment can be rebuilt from git. Kubernetes workloads are deployed onto the EKS cluster from `backend/k8s/`.

## Layout

```
infrastructure/
├── bootstrap/            # One-time: S3 state bucket + DynamoDB lock table
├── environments/
│   ├── staging.tfvars            # Committed, non-secret sizing per environment
│   ├── staging.s3.tfbackend      # Remote state location per environment
│   ├── production.tfvars
│   └── production.s3.tfbackend
├── modules/
│   ├── networking/       # VPC, public/private subnets per AZ, NAT, routing
│   ├── kubernetes/       # EKS cluster + managed node group across AZs
│   ├── database/         # RDS PostgreSQL (Multi-AZ, PITR, managed master secret)
│   ├── cache/            # ElastiCache Redis (replica + automatic failover)
│   ├── storage/          # S3 assets bucket, versioned, replicated to the DR region
│   └── backup/           # AWS Backup plan, DR-region vault, weekly restore tests
├── main.tf               # Wires the modules together
├── providers.tf          # Primary region + `aws.dr` alias for the DR region
├── variables.tf
├── outputs.tf
└── versions.tf           # Terraform/provider versions, S3 backend
```

## Prerequisites

- Terraform `>= 1.6`
- AWS credentials for the target account with permission to manage the resources above
- Commit the generated `.terraform.lock.hcl` after the first `init` so provider versions are pinned

## First-time setup (per AWS account)

```bash
terraform -chdir=infrastructure/bootstrap init
terraform -chdir=infrastructure/bootstrap apply
```

## Day-to-day workflow

```bash
ENV=staging   # or production

terraform -chdir=infrastructure init -backend-config=environments/$ENV.s3.tfbackend -reconfigure
terraform -chdir=infrastructure plan  -var-file=environments/$ENV.tfvars -out=$ENV.tfplan
terraform -chdir=infrastructure apply $ENV.tfplan
```

- Every change goes through a pull request; `Infrastructure CI` runs `terraform fmt -check` and `terraform validate`.
- Review the plan before applying. Any `destroy` of `module.database` or `module.backup` resources needs a second reviewer.
- Production RDS has `deletion_protection` enabled; `skip_final_snapshot` is off.

## Secrets

No secrets live in this directory or in Terraform variables:

- The RDS master password is generated by RDS and stored in Secrets Manager (`db_master_secret_arn` output).
- Application secrets (JWT, Stellar keys, APM keys) are managed in AWS Secrets Manager and synced into Kubernetes; see `docs/infrastructure-as-code.md` §6.

## Backups and DR

`modules/backup` implements the backup policy from `docs/disaster-recovery-plan.md`:

| Schedule | Retention | Copy |
| --- | --- | --- |
| Daily 02:00 UTC | 30 days | DR region vault |
| Monthly, 1st at 03:00 UTC | 1 year | DR region vault |
| RDS automated backups (PITR) | 7 days | — |
| Restore test: Sundays 05:00 UTC | Test instance deleted after validation | — |

Failed backup, copy or restore jobs publish to the `<env>-backup-events` SNS topic (`backup_alert_emails` subscribes addresses).

To rebuild in the DR region after a regional outage, follow the "Data center / region loss" scenario in `docs/disaster-recovery-plan.md`.
